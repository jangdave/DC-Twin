# 21. 웹 직접 시뮬레이션 명세

- 상태: 채택 (2026-11-03). 1단계(브라우저 간이 모델) 구현·확인 완료, 2단계(로컬 계산 서버 연결)는 구현 전
- 목적: 웹 보기 화면에서 사용자가 CRAC 팬 속도와 랙 전력을 직접 바꾸면 그 결과(입구 온도, 알람, 전력 합계)가 바로 화면에 나오게 한다. 배포한 정적 페이지(서버 없음)에서도 동작해야 한다.
- 관련: [18 웹 보기 화면 명세](18_web_viewer_spec.md), [11 데이터 규격](11_data_spec.md), [ADR-011](decisions/ADR-011-webgl-viewer.md), [E5 보정 모델](../experiments/results/E5_surrogate_residual_model.md)
- 시뮬레이션 값은 시각화 목적이며 공학적 정확성을 주장하지 않는다.

## 1. 두 방식

| 방식 | 계산하는 곳 | 모델 | 어디서 쓰나 | 상태 |
|---|---|---|---|---|
| 직접 시뮬레이션(간이) | 이 브라우저 | 센서 생성기의 L0 모델(1차 지연 식)을 JS로 옮긴 것 | 배포한 정적 페이지, 로컬 | 구현됨 |
| 로컬 계산 서버 | 이 컴퓨터의 파이썬 서버 | L1(열 시뮬레이션) 또는 L2(보정 모델 포함), 서버에서 고르는 것 | 로컬만(서버가 있어야 함) | 구현 전(4장) |

기본은 간이 방식이다. 서버가 있으면 같은 화면이 서버 값으로 바꿔 보이게 하는 것이 2단계다.

## 2. 간이 방식(1단계)

### 2.1 모델
- 원본: `sim/sensors/dct_sensors/{config,solvers,alarms,scenarios,generator}.py`. 이 중 L0 온도 모델, 알람 상태기계, 시나리오 4종, 집계 계산을 `web/viewer/src/sim/`으로 옮겼다.
- L0: 냉각이 줄면 랙 입구 온도의 목표가 오르고, 온도는 목표를 향해 시간 상수 60초의 1차 지연으로 변한다. 출구 온도, CRAC 급기·회수 온도, 랙 전력, 팬 속도, 집계(IT 전력, 냉각 전력, PUE)를 만든다. 보정 모델(AI)은 쓰지 않아 신뢰 막대와 90% 구간이 나오지 않는다(화면에 이유를 적었다).
- 한 단계는 시뮬레이션 1초다. 속도 1x, 2x, 5x, 10x는 실제 1초에 계산할 단계 수다. 한 프레임에 최대 20단계까지만 계산한다(느린 기기와 탭 전환 뒤 몰림 방지).
- 난수는 시드(7)를 고정한다. 새로 열 때마다 같은 랙별 기본 전력과 오르내림이 나온다.

### 2.2 조작과 화면
- 위의 "직접 시뮬레이션" 단추(또는 주소 `?mode=sim`)로 들어가고 "녹화 재생"으로 돌아온다. 센서 저장소는 모드를 바꾸면 비운다.
- 시나리오 4종: 정상 운전, 냉각 장치 고장, 전력 급증, 팬 이상. 선택하면 처음부터 시작하고 모든 조작이 되돌아간다. 시나리오가 정한 시각에 이벤트(예: 60초에 CRAC_02 정지)가 일어난다.
- 직접 조작: CRAC 8기의 팬 속도(0~100%), 줄별 랙 전력 배수(0~200%), 선택한 랙 하나의 전력 배수(0~300%). 슬라이더를 움직이면 바로 반영하고 "조작 기록"에 시각과 함께 남긴다. 시나리오 이벤트가 값을 바꾸면 슬라이더가 따라간다.
- 오른쪽 위의 "시나리오 설명" 카드는 녹화 재생과 직접 시뮬레이션에서 같이 쓴다: 시나리오 이름과 설명, 지금 가장 높은 입구 온도 랙(누르면 선택), 지금 알람 수, 첫 알람 시각, "일어나는 일" 목록(녹화 재생에서는 누르면 그 시각으로 이동).
- 재생 조작은 녹화 재생과 같은 단추(일시정지, 속도)를 쓴다. 시간 막대와 반복은 숨기고 경과 시간만 보인다.
- 알람은 센서 생성기와 같은 규칙으로 판정한다(연속 2번 넘어야 올림, 0.5도 아래로 내려와야 해제). 알람 목록, 3D 테두리, 외관의 건물 경고등이 같은 저장소를 읽는다.

### 2.3 정확성 점검
- 파이썬 L0와 값 비교: `web/viewer/tools/make_sim_fixture.py`가 잡음 0으로 두 시나리오를 200초 돌린 기준 자료(`test/fixtures/sim_l0.json`)를 만들고, `test/sim.test.js`가 JS 결과와 비교한다. 센서 204개와 집계 5개가 소수 3자리 반올림 차이(0.0015) 안에서 같고, 알람 전이(냉각 장치 고장 29건, 전력 급증 19건)가 일치한다.
- 알람 규칙은 센서 생성기와 게이트웨이가 쓰는 `sim/sensors/tests/alarm_vectors.json`을 JS도 같이 쓴다.
- 화면 확인(`tools/ui_check.mjs`): 시작, 슬라이더 개수, 첫 값, CRAC_02를 끄면 가장 높은 입구 온도가 3도 이상 오름과 알람 발생, 조작 기록, 시나리오 전환 시 초기화, 모드 전환.
- 한계: L0는 열 흐름을 계산하지 않고 식으로 흉내 낸다. 랙 위치별 차이는 줄 끝 보정 정도뿐이고 CRAC 한 대의 영향은 그 CRAC가 맡은 통로 전체에 같은 비율로 퍼진다. 보정 모델(E5)이 배운 OpenFOAM 결과와는 맞춰지지 않았다(L2에서만 보정).

## 3. 결정과 이유
| 결정 | 이유 | 다른 방법 |
|---|---|---|
| 센서 생성기의 L0를 JS로 옮김 | 이미 "기준선이자 대체 수단"으로 설계된 작은 모델이라 식이 짧고(약 100줄) 파이썬 원본과 값을 직접 비교할 수 있다 | Warp(L1)를 WebGPU로: 작업이 매우 크고 브라우저 지원이 일정하지 않다 |
| 보정 모델(AI)을 브라우저에 넣지 않음 | 모델 파일(scikit-learn)을 JS로 옮기려면 별도 변환과 검증이 필요하고, 2단계 서버에서 L2로 보여 줄 수 있다 | ONNX 변환: 가능하지만 이번 범위 밖 |
| 시드 고정 | 시연이 매번 같아야 설명하기 쉽다 | 매번 무작위: 재현이 안 된다 |
| 간이 모델임을 화면에 표시 | 시각화용 값을 정확한 계산으로 오해하지 않게 | — |

## 4. 로컬 계산 서버(2단계)
구현 전이다. 방향만 적는다.
- 파이썬 서버(`sim/sensors`에 추가)가 센서 생성기(L0, L1, L2 중 선택)를 실제 시간으로 돌리고, 게이트웨이와 같은 형식의 메시지(`snapshot`, `sample`, `alarm`, `aggregate`, `scenario`)를 WebSocket으로 보낸다.
- 웹이 보내는 조작 메시지(`control`: CRAC 팬 속도, 랙 전력 배수, 시나리오 시작)를 받아 같은 규칙으로 적용한다.
- 웹은 기존 라이브 연결(`?live=ws://127.0.0.1:...`)을 확장해 같은 조작 패널을 쓴다. 이 컴퓨터(127.0.0.1)와 `wss://`만 허용하는 기존 규칙을 유지하고, 조작 메시지는 허용한 장비 이름과 값 범위만 받는다.
- 이 서버는 L2일 때 보정 모델의 90% 구간과 신뢰 등급을 같은 메시지에 실어 보내므로 신뢰 막대도 보인다.

## 5. 열린 문제
- 간이 모델의 시간 상수(60초)와 계수는 "그럴듯하게" 정한 값이다. 열 시뮬레이션(L1) 결과의 응답 속도와 맞춰 보는 일은 하지 않았다.
- 슬라이더가 많은 좁은 화면(휴대폰)에서 조작 패널을 어떻게 접을지는 구현 때 화면을 보고 정한다.
