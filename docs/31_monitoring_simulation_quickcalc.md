# 31. 모니터링, 시뮬레이션, 간이 계산의 역할 다시 나누기

- 상태: 채택 (2026-11-10). 6장 순서로 구현한다. **같은 날 방향 조정: 정확도 검증([32](32_kit_accuracy_verification.md))을 먼저 하고, 작업 API는 검증 실행기로 같이 쓴다. 화면 연결(3~5단계)은 검증 뒤.**
- 목적: 세 메뉴가 각각 **어디서 온 값을 보여 주는지**를 분명히 나눈다. 모니터링은 현장(장비 상태와 센서)의 지금 값, 시뮬레이션은 사용자가 정한 조건으로 서버가 새로 계산한 값, 간이 계산은 모니터링의 지금 상태에서 몇 가지만 바꿨을 때의 빠른 예측이다.
- 관련: [27 웹 화면 계획](27_web_ui_redesign_plan.md) 16.5~16.10장(데이터 출처 어댑터, 서버), [21 직접 시뮬레이션](21_web_simulation_spec.md), [11 데이터 규격](11_data_spec.md), [30 구조 검토](30_architecture_review.md) M12(열 계산 코드 위치), `server/README.md`(인증)
- 표기: 가상 시설이다. 모든 계산 결과는 시각화 목적이며 공학적 정확성을 주장하지 않는다.

## 1. 사용자 요청과 결정 (2026-11-10)

요청:
- 모니터링: 실제 센서와 장비 작동에 따른 온도, 전력, 공기 흐름을 보여 준다.
- 시뮬레이션: 조건을 상세히 정하고, 그 조건으로 서버에서 돌린 결과를 보여 준다. 오래 걸리면 로딩이나 남은 시간 창으로 확인한다.
- 간이 계산: 모니터링 상황에서 팬 속도, 온도 설정을 바꾸면 바뀐 부분만 빠르게 계산해 보여 준다.

사용자가 고른 것:
| 질문 | 결정 | 다른 방법(고르지 않음) |
|---|---|---|
| 모니터링 값의 출처 | **서버 실시간 값**. 물리 센서가 없으므로 서버의 센서 생성기가 현장 역할을 한다. 서버가 없으면 녹화 재생으로 대신하고 "기록"이라고 표시한다 | MQTT 실제 장비 입력부터 정리 / 녹화 재생 유지 |
| 시뮬레이션의 서버 계산 | **Warp 열 계산**(`hall60_sim`)으로 조건마다 새로 계산 | 보정 모델(L2)만 / 둘 다 고르게 |
| 순서 | **설계 문서 → 서버 작업 API → 화면** | 간이 계산부터 / 한 번에 |
| 서버 위치 (2차 결정) | **로컬**(`server/run_local.ps1`, `127.0.0.1`). GPU 서버 배포는 나중 | Docker로 바로 배포 |
| Omniverse 활용 (2차 결정) | **쓸 수 있는 곳은 최대한 쓴다**(8장) | Warp만 독립 실행 |
| 서버 형태 (3차 결정) | **Omniverse Kit을 쓰는 로컬 서버.** Kit 앱이 장면(USD)을 열고 센서 생성기와 작업 실행기를 Kit 안에서 돌린다(8장) | 파이썬 서버만 두고 Kit은 선택 |
| 정확도와 시간 (3차 결정) | **시뮬레이션은 오래 걸려도 정확하게, 간이 계산은 빠르게.** 시뮬레이션은 시간 변화는 Warp 열 계산, 최종(정상 상태) 값은 OpenFOAM(난류, 부력이 있는 공기 흐름 계산)으로 낸다. 간이 계산은 브라우저에서 즉시 | 시뮬레이션도 Warp만(빠르지만 열 쏠림을 작게 봄) |

## 2. 세 메뉴 한눈에

| | 모니터링 | 시뮬레이션 | 간이 계산 |
|---|---|---|---|
| 묻는 것 | 지금 어떤가 | 이런 조건이면 어떻게 되나 | 지금 상태에서 팬·온도만 바꾸면 |
| 값의 출처 | Kit 서버 실시간(센서 생성기 + 장비 상태, 보정 모델 L2) | Kit 서버 작업(Warp 시간 변화 + OpenFOAM 정상 상태) | 브라우저 계산(L0) |
| 시작 상태 | 현장 | 사용자가 정한 조건(기본값은 기준 상태) | 모니터링의 지금 값 |
| 바꿀 수 있는 것 | 없음(보기만). 장비 조작은 기존처럼 서버 연결 때만 | 상세 조건(3장) | CRAC별 팬 속도, 급기 온도 |
| 걸리는 시간 | 실시간 | 약 10~15분(진행률과 남은 시간 표시). Warp 단계는 1분 이내라 먼저 미리보기로 보인다 | 1초 이내(조절하면 바로 다시 계산) |
| 서버가 없을 때 | 녹화 재생("기록" 표시) | 미리 계산한 결과 12개만 보이고 조건 계산 단추는 꺼짐(이유 표시) | 그대로 동작(녹화의 지금 값에서 시작) |
| 공기 흐름 | 장비 상태(CRAC별 팬)에 맞춰 흐름장을 섞음 | 계산한 조건의 흐름 | 바꾼 팬 값으로 흐름장을 섞음 |

## 3. 시뮬레이션 조건

| 조건 | 범위 | 기본값 | 계산에 들어가는 곳 |
|---|---|---|---|
| CRAC별 켜고 끄기 | 8대 각각 | 모두 켜짐 | 흐름 계산(꺼진 CRAC는 빨아들이지 않음) |
| CRAC별 팬 속도 | 0~100 % (서버 조작과 같은 범위) | 100 % | 흐름 세기, 냉각 비율 |
| 급기 온도 | 14~27 °C (서버 조작, 간이 계산과 같은 범위) | 18 °C | 급기구 온도 |
| 부하 | 줄별(6줄) 또는 랙별(60기) 전력 배수. 서버가 받는 범위는 0~300 %, 화면 기본 슬라이더는 50~150 % | 100 % | 랙 발열 |
| 고장 이벤트 | 대상 CRAC, 시각(초) | 없음 | 그 시각부터 해당 CRAC 끄기 |
| 길이 | 60~1800 초 | 300 초 | 계산 시간 |

조건은 JSON 하나로 보내고 서버가 범위를 다시 검사한다. 같은 조건이면 결과를 다시 쓴다(조건의 해시를 키로 저장).

## 4. 서버 작업 API (시뮬레이션)

| 요청 | 하는 일 |
|---|---|
| `POST /api/sim/jobs` | 조건을 받아 작업을 만든다. 응답: `{ id, state, position }`. 같은 조건의 결과가 있으면 바로 `done` |
| `GET /api/sim/jobs/<id>` | 상태: `queued` / `running` / `done` / `failed` / `cancelled`, 단계(흐름 계산, 온도 계산, 센서 기록 작성), 진행률(0~1), 남은 시간(초, 추정) |
| `DELETE /api/sim/jobs/<id>` | 취소 |
| `GET /api/sim/jobs/<id>/result` | 결과 녹화(지금 녹화와 같은 형식). 화면은 미리 계산한 결과와 같은 재생기로 연다 |

규칙:
- 접근 토큰이 필요하다(GPU를 쓰므로 공개하지 않는다). 기존 인증과 요청 제한을 그대로 쓴다.
- GPU 작업은 한 번에 하나, 대기열은 최대 3개. 넘치면 거절하고 이유를 돌려준다.
- 남은 시간은 단계별 실제 속도로 추정한다. 측정값(RTX 5090): 흐름 풀이 3.7~7.1초, 900초 계산 약 4.3초(`experiments/results/E0` 2.18장). 처음 실행은 Warp 준비 시간이 더해진다. 추정은 첫 몇 초 동안 "계산 중"으로만 보인다.
- 진행 상황은 화면이 1초마다 묻는다(WebSocket으로 밀어 주는 것은 나중에. 단순한 쪽을 먼저).
- 작업 파일은 gitignore된 `sim/out/jobs/`에 둔다. 오래된 결과는 개수 상한으로 지운다.

### 4.1 정확한 계산의 단계 (3차 결정)

> **2026-11-10 개정(V4~V5, docs/32):** 아래 표는 처음 계획이다. 검증 결과에 따라 실제 구성은 **OpenFOAM이 팬 상태마다 공기 흐름을 풀고, 우리 온도 계산(열 보존 fv, 다공질 랙)이 그 흐름으로 시간 변화와 센서 값을 낸다**로 바꿨다(`sim/sensors/dct_sensors/precise.py`, 첫 실행 [V5](../experiments/results/V5_precise_job_first_run.md)). 단계 순서는 조건 → USD 층 → 공기 흐름(OpenFOAM) → 시간 변화와 센서 값 → 결과다.

| 단계 | 실행 | 시간(측정값 기준 추정) | 결과 |
|---|---|---|---|
| ① 조건 → USD 층 | Kit | 1초 이내 | `job.usda`(조건 기록, 재현용) |
| ② 시간 변화 | Kit 안 Warp 열 계산 + 센서 생성기 | 약 20~40초(Kit 안 300초 계산 15.1초, 센서 생성 20.4초: `E0` 2.24장) | 녹화. **미리보기**로 바로 볼 수 있다 |
| ③ 정상 상태 | OpenFOAM(WSL, 16코어) 메시 + SIMPLE 반복 | 약 8~12분(10 cm 격자, 정상 450초, CRAC 2대 정지 672초, 다른 조건 451~634초: `openfoam_baseline/README.md`) | 랙 입구 온도(정상 상태) |
| ④ 맞추기 | Kit | 몇 초 | ②의 녹화 끝 부분을 ③의 값으로 보여 주고, 차이를 함께 기록한다(값을 섞어 숨기지 않는다) |

- 진행 창은 단계 이름, 단계별 진행률(OpenFOAM은 잔차가 수렴 기준까지 내려온 정도), 전체 남은 시간을 보인다. ② 끝나면 "미리보기 보기" 단추가 켜진다.
- OpenFOAM은 수렴 기준(p_rgh 1e-4, U 1e-5, T 1e-6)을 못 맞추면 "수렴 못 함"으로 표시하고 ②의 값만 쓴다.
- OpenFOAM은 정상 상태만 푼다. 시간에 따른 변화(고장 직후 몇 분)는 ②의 Warp 값이다. 화면에 어느 값이 어느 계산인지 적는다.
- 한 번에 OpenFOAM 하나만 돌린다(둘을 같이 돌리면 20배 넘게 느려진 기록이 있다).
- WSL은 유휴 상태에서 가상 머신이 내려가 계산이 죽는 문제가 있었다. 기존 `keepalive.py` 방식으로 계산 중에는 WSL을 붙잡아 둔다.

## 5. 화면

**모니터링**
- 서버에 연결되면 실시간 값. 위 띠에 "실시간"과 연결 상태를 보인다. 서버가 없으면 녹화 재생이고 "기록(서버 없음)"이라고 보인다.
- 재생 막대는 기록일 때만 보인다(실시간에는 되감기가 없다).

**시뮬레이션**
- 조건 창: 3장의 조건. CRAC 8대는 홀 배치 그림 위에서 누르는 칸, 부하는 줄 단위가 기본이고 랙 단위는 펼쳐서 고친다.
- "서버에서 계산" 단추 → 진행 창: 단계, 진행 막대, 남은 시간, 취소. 창을 닫아도 계산은 이어지고 위 띠에 작은 진행 표시가 남는다.
- 끝나면 결과를 재생한다. 기준 상태와 나눠 비교할 수 있다(지금의 나눠 비교 재사용).
- 미리 계산한 결과 12개는 "예시"로 남긴다(서버 없이도 보이는 것).

**간이 계산**
- 시작할 때 모니터링의 지금 값(온도, 팬, 급기)을 그대로 가져온다.
- 바꿀 수 있는 것: CRAC별 팬 속도, 급기 온도. 바꾸면 바로 다시 계산하고 "바뀌기 전과 차이"를 색과 숫자로 보인다.
- "같은 조건으로 서버에서 정밀 계산" 단추로 시뮬레이션 조건 창에 옮겨 간다.

## 7. 한계와 위험

- **물리 센서가 없다.** 모니터링의 "실시간"은 서버의 센서 생성기가 만든 값이다. 나중에 실제 장비가 같은 MQTT 토픽(`dct/v1/...`)으로 보내면 그대로 받을 수 있게 형식은 맞춰 둔다.
- **공개 페이지(GitHub Pages)에는 서버가 없다.** 공개 페이지에서는 모니터링이 기록, 시뮬레이션은 예시 12개만 보인다. 서버 계산은 로컬이나 GPU 서버에서만 된다.
- **열 계산 코드가 `experiments/`에 있다**(`docs/30` M12). 2단계에서 작업 실행기가 이 코드를 부른다. `sim/` 패키지로 옮기는 일은 따로 한다.
- "정확한 값"도 시각화 목적이다. OpenFOAM은 우리 Warp 모델보다 물리가 많지만(난류, 부력, 운동량) 메시 의존성 시험이 부족하고(10 cm, 20 cm만), 경계 조건이 단순하다(`openfoam_baseline/README.md` "어긋나는 가정"). 공학적 정확성을 주장하지 않는다.
- OpenFOAM 계산 중에는 CPU 16코어를 거의 다 쓴다. 그동안 다른 무거운 일을 하면 느려진다.
- 공기 흐름은 지금 미리 계산한 흐름장(정상 1개 + CRAC마다 멈춘 장 8개)을 팬 값으로 섞는 근사다(`airflow.js` `_compose`). 시뮬레이션 결과의 흐름장을 서버가 새로 보내 그리는 것은 6장 뒤의 일이다.

먼저 구분: **실제 센서 데이터는 Omniverse에도 없다.** Omniverse는 장면(USD)과 계산·렌더 실행 환경을 준다. 센서 값은 우리 열 계산이 장면의 센서 위치에서 만든다. 이전 실험(`experiments/results/E0` 2.24, 2.25장)에서 확인한 것을 바탕으로 쓸 곳과 쓰지 않을 곳을 나눈다.

| 쓰는 곳 | 방법 | 근거 |
|---|---|---|
| **조건을 USD로** | 시뮬레이션 조건을 장면 위에 얹는 USD 층(override layer)으로 만든다. CRAC의 켜짐·팬 속도, 랙 전력 배수, 급기 온도를 `dct:` 속성으로 적는다. 계산은 이 층을 얹은 장면을 읽는다 | CLAUDE.md "시뮬레이션 입력은 장면 USD에서 읽는다". 나중에 Unreal에서 같은 층을 열어 조건을 볼 수 있다. 결과마다 조건 파일이 남아 재현된다 |
| **센서 위치는 USD 앵커** | 지금처럼 장면의 `Anchors/Sensor_*` prim 위치에서 온도를 읽는다(바꾸지 않음) | `docs/09` |
| **Kit이 로컬 서버의 실행 환경** (3차 결정) | `server/run_local.ps1`이 Kit 앱을 띄우고, Kit 안에서 장면을 연 채로 센서 생성기(실시간), 작업 실행기(시뮬레이션), 웹 연결(WebSocket, REST)을 돌린다. Kit에 없는 파이썬 패키지(scipy, websockets)는 저장소 밖 `D:/omniverse-kit/pydeps`에 둔다 | 2.24장: Kit 안 결과가 독립 실행과 같다(센서 최대 차이 0.0~0.001). Kit 시작 약 12초, 계산은 독립보다 느리다(15.1초 대 4.4초). 창 없이 띄울 수 있는지는 2단계에서 확인한다 |
| **Warp** | 열 계산(`hall60_sim`)은 Omniverse의 Warp로 돈다(그대로) | 2.18장 |

| 쓰지 않는 곳 | 이유 |
|---|---|
| Flow(연기·열 확장)를 센서 값 원천으로 | 2.25장: 온도 단위가 정의되어 있지 않고, 내보낸 격자에 세계 위치가 없고, 값이 출렁인다 |
| ovrtx로 CCTV 화면 | 웹 CCTV는 브라우저가 그린다. 서버에서 그리는 것은 `docs/29`에서 GPU 서버와 인증이 갖춰진 뒤로 미뤘다 |

구현 순서는 6장에 이렇게 들어간다: 2단계 처음에 **Kit 서버 동작 확인**(창 없이 띄우기, Kit 안에서 WebSocket 서버와 Warp 동시 실행, 종료 정리)을 하고, 되면 조건 → USD 층 → Kit 안 Warp → OpenFOAM 순서로 붙인다. Kit을 쓸 수 없는 환경(Kit 미설치, GitHub Actions)에서는 지금의 파이썬 서버가 그대로 대신한다(시험도 이쪽으로 돈다).
