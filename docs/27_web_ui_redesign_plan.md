# 27. 웹 화면 개편 계획 (목적 중심 메뉴, 모바일과 PC, 3D 조작, 로딩 화면)

- 상태: 초안 (2026-11-04, 같은 날 9~11장 추가). 확정되면 "채택"으로 바꾼다.
- 목적: 플랫폼을 쓰는 이유 세 가지에 맞춰 메뉴와 화면 배치를 다시 짜고, 휴대폰과 PC 모두에서 3D 조작이 자연스럽게 하도록 한다. 첫 로딩 때 어색한 화면이 보이지 않게 로딩 화면을 둔다.
- 관련: [18 웹 보기](18_web_viewer_spec.md), [21 직접 시뮬레이션](21_web_simulation_spec.md), [25 UX 구조](25_web_ux_layout.md), [24 디자인 시스템](24_web_design_system.md)

## 1. 쓰는 이유 세 가지와 화면의 대응

| 목적 | 지금 있는 것 | 부족한 것 |
|---|---|---|
| ① 현장 센서 감시와 통제 | 센서 204개, 알람 상태기계, 팬과 전력 배수 조작, 로컬 서버 연결 | 화면에서 바로 보이는 알람, 이름으로 장비 찾기 |
| ② 시뮬레이션으로 이상상황 대비 | 시나리오 4종, 기류 보기 | 같은 시나리오를 두 조건으로 비교, 대응 순서 안내 |
| ③ 시뮬레이션으로 전력 사용량 감축 | 계산 엔진이 IT 전력, 냉각 전력, 설비 전력, 누적 kWh를 이미 계산함(화면에는 일부만 표시) | 전력 중심 화면, 줄였을 때 입구 온도가 어떻게 되는지 비교 |

한계: 냉각 전력 계산은 아주 단순한 모델(CRAC 팬 1대 최대 3 kW, 기본 1 kW)이다. 줄어드는 **방향**을 보여 줄 뿐 실제 절감량을 말하지 않는다. 화면에는 "시각화 목적, 공학적 정확성 아님"을 계속 보인다. 공급 온도를 바꾸는 조작과 냉각 효율 모델은 가정을 문서에 적고 마지막에 넣는다.

## 2. 참고한 사례에서 가져온 것 (배치와 개념만, 코드와 그림은 쓰지 않음)

확인한 날짜: 2026-11-04. 글과 이미지, 영상을 직접 확인했다. 홍보 자료는 연출이 섞여 있어 사용성이 검증된 것은 아니다.

| realvirtual WEB(공장용, AGPL-3.0) | 3D를 화면 전체로 두고 모든 것을 떠 있는 카드로 둠. 위 가운데 핵심 수치 카드(작은 추세선), 왼쪽 세로 아이콘 줄(알람 숫자 배지), 오른쪽 알람 카드(색으로 종류 구분, 열기와 닫기), 아래 가운데 검색창, 카메라 단추 |

| NVIDIA 블루프린트(홍보) | "만들기, 시험, 시뮬레이션" 흐름, 카메라 썸네일, X·Y·Z 단면과 슬라이더, 보이기 토글(천장, 랙 등), 발열량 슬라이더와 전력 색 막대, 총 전력을 큰 숫자로 |

## 4. 화면 배치

공통: 3D 화면이 전체를 채우고, 그 위에 카드가 뜬다. 영역을 나누는 지금의 틀(위, 오른쪽, 아래)을 없앤다.

**PC (너비 901px 이상)**
- 위 가운데: 핵심 수치 카드(IT 전력, 냉각 전력, PUE, 누적 kWh)와 작은 추세선
- 왼쪽: 세로 아이콘 줄. 누르면 옆으로 패널이 열리고 다시 누르면 닫힌다. 알람 숫자 배지
- 오른쪽 위: 시나리오 이름과 연결 상태, 도움말
- 오른쪽: 알람 카드(종류별 색, 열기, 닫기)
- 아래 가운데: 장비 검색창(랙 60기, CRAC 8기)
- 오른쪽 아래: 시점(썸네일), 보이기 켜고 끄기, 재생과 속도 작은 묶음
- 왼쪽 아래: 범례. 구석에 면책 문구(상시 표시)

**모바일 세로 (너비 700px 이하)**
- 3D 화면 전체. 위에는 한 줄 띠(제목, 시나리오 이름, 알람 배지)
- 핵심 수치는 PUE 하나로 줄이고, 누르면 나머지가 펼쳐진다
- 아래에서 올라오는 시트(bottom sheet): 접힘(요약 한 줄) / 반쯤 / 전체 세 단계. 탭은 아래 줄
- 장비를 탭하면 시트가 "모니터링 > 장비"로 올라오고, 접으면 3D가 다시 전체로 보인다
- 터치 영역은 44px 이상

**모바일 가로, 태블릿 (701~900px)**: 3D를 왼쪽, 시트를 오른쪽 패널로 둔다.

## 5. 3D 조작

| 동작 | 마우스(PC) | 터치(모바일) |
|---|---|---|
| 돌리기 | 왼쪽 버튼 끌기 | 한 손가락 끌기 |
| 이동과 확대 | 오른쪽 버튼 끌기, 휠 | 두 손가락 끌기와 모으기 |
| 선택 | 클릭 | 탭 |
| 요약 보기 | 올려 놓기(툴팁) | 길게 누르기 |
| 장비로 이동 | 두 번 클릭 | 두 번 탭 |
| 전체 보기로 | 빈 곳 두 번 클릭, `Esc` | 빈 곳 두 번 탭 |
| 시점 바꾸기 | `1`, `2`, `3` | 시점 단추 |
| 선택 장비로 이동 | `F` | (두 번 탭) |
| 재생과 멈춤 | `Space` | 재생 단추 |

- 카메라 이동은 부드럽게(약 0.6초 보간). 선택한 장비에는 고리를 그린다.
- 3D 화면에는 `touch-action: none`을 적용해 페이지 스크롤과 겹치지 않게 한다.
- 처음 한 번만 짧은 조작 안내를 보이고, 이후에는 도움말에서만 보인다.
- 3D가 열리지 않는 기기를 위해 "목록으로 보기"(알람 목록과 장비 표)를 둔다.

## 6. 상단과 하단

- "녹화 재생" 모드 단추를 없앤다. 기본은 직접 시뮬레이션, 로컬 서버는 "서버 연결" 하나로 둔다.
- **녹화 데이터(L2 신뢰 구간)는 지우지 않는다**(결정, 2026-11-04). 파일과 읽는 코드를 남기고 "보정 모델 비교", "기록 보기"로 이어 간다.
- 하단 재생바를 없앤다. 재생, 정지, 속도(1x, 2x, 5x), 처음부터 다시는 3D 위 작은 묶음으로 옮긴다. 반복과 시간 막대는 기본 화면에서 없앤다.
- 시간 막대는 "이상 대비" 탭 안에서만 얇게 보인다(시나리오 진행과 사건 표시).
- 면책 문구("시각화 목적, 공학적 정확성 아님")는 없애지 않고 화면 구석에 상시 보인다.

## 7. 로딩 화면

- 첫 HTML에 CSS만으로 그려서, 자바스크립트가 로드되기 전에도 보인다.
- 내용: 제목, 한 줄 설명, 단계 표시(화면 준비, 건물 모델, 기류 데이터, 완료), 진행 막대, 면책 문구.
- 진행 막대는 모델 받기의 진행률(바이트)로 움직이고, 모를 때는 단계만 보인다.
- 첫 장면이 그려진 뒤 부드럽게 사라진다. 움직임 줄이기 설정이면 애니메이션 없이 바로 바뀐다.
- 실패하면 "다시 시도"와 "저화질로 열기"를 보인다. 3D(WebGL)를 쓸 수 없는 기기는 "목록으로 보기"로 안내한다.
- 용량이 큰 홀 모델은 지금처럼 저사양에서 나중에 받으므로, 로딩 화면은 외관이 보이는 시점까지만 막는다.

## 8. 진행 순서와 확인 방법

| 단계 | 내용 | 확인 |
|---|---|---|
| 1 | 로딩 화면 | 동작 확인 테스트(처음 화면에 로딩이 보임, 장면 준비 후 사라짐, 실패 시 안내), 용량 한도 |
| 2 | 모바일 시트와 터치 조작 | 화면 크기별 캡처, 터치 이벤트 시험 |
| 3 | PC 왼쪽 아이콘 줄, 단축키, 카메라 이동, 검색 | 동작 확인 테스트 |
| 4 | 에너지 탭(이미 있는 계산값 표시) | 값 비교 테스트 |
| 5 | 이상 대비 탭의 전후 비교와 대응 순서 | 같은 시나리오 두 조건 값 비교 |
| 6 | 3D 위 값 표시, 단면 보기, 용량 탭 | 화면 확인 |
| 7 | 공급 온도 조작과 냉각 효율 모델(가정을 문서에 기록) | 값 비교, 가정 명시 |

각 단계는 PR 하나씩 병합한다. 확인하지 못하는 것: 실제 휴대폰의 속도와 손가락 조작(헤드리스 브라우저로는 화면 크기와 터치 이벤트까지), Firefox와 Safari. 사용하는 기기에서 직접 보고 알려 주어야 한다.

## 9. 화면 흐름 개정 (2026-11-04 요청): 외관 → 서버실 기본 보기 → 시뮬레이션 메뉴

요청: 건물을 눌렀을 때 바로 시뮬레이션이 나오지 않게 한다. 먼저 외관처럼 **실제 서버실 내부를 볼 수 있는 기본 화면**을 보이고, 시뮬레이션은 메뉴에서 켠다. 외관에서는 주변 도시와 함께 보이고 건물 전체 전력 사용량 같은 내용만 조금 보인다.

### 9.1 단계별 화면

| 단계 | 3D 화면 | 카드와 메뉴 |
|---|---|---|
| ① 외관 | 건물과 주변 도시(지금 구현됨) | 작은 카드 하나: **총 전력(IT와 냉각 합), PUE, 알람 있음 표시**만. 최고 입구 온도와 알람 개수 표는 뺀다. "들어가기" 단추 |
| ② 서버실 기본 보기 | **실제 서버실처럼**: 바닥, 벽, 천장, 천장 조명, 랙과 CRAC의 실제 재질. 온도 색칠과 공기 흐름 입자는 **꺼짐** | 왼쪽 아이콘 줄: 모니터링, **시뮬레이션**, **CCTV**. 시뮬레이션은 꺼진 상태로 시작 |
| ③ 시뮬레이션 켬 | 같은 방 위에 온도 색, 공기 흐름이 켜짐 | 이상 대비, 에너지, 용량, 조작 메뉴가 열림. 끄면 ②로 돌아감 |
| ④ CCTV | 구역별 가상 카메라 화면 | 10장 |

- 외관 카드의 값은 평상시 모델(브라우저 시뮬레이션의 "정상 가동")에서 온다. 값 출처를 카드 아래 작은 글씨로 보인다("간이 모델 값").
- 서버실 기본 보기에서도 랙을 누르면 장비 정보(이름, 전력 등 실시간 값)는 보인다. 온도 색칠만 꺼져 있다.
- 서버실 기본 보기의 카메라는 처음에 입구 쪽에서 홀을 바라보는 시점이다(지금의 "비스듬히"는 시뮬레이션용으로 둔다).

### 9.2 서버실을 실제처럼 보이게 하는 방법

- 지금 웹 서버실 화면에는 **방이 없다**(검은 배경에 점선 상자). 이유: 웹은 랙과 CRAC과 통로 지붕만 올리고, 바닥, 벽, 천장, 조명은 올리지 않았다.
- 그 방은 이미 USD 장면에 있다(`Shell`: 바닥, 벽 4개, 천장, 걸레받이, 바닥 표시, 조명 42개 / 삼각형 약 1,252개, docs/09). 같은 내용을 웹용 glb로 내보내 쓴다(외관 glb와 같은 방식: Draco 압축, 평평한 색, 필요한 곳만 그림).
- 바닥, 벽, 천장 그림은 이미 저장소에 있는 CC0 자료(Tiles040, PaintedPlaster017, OfficeCeiling001, Metal027; `ASSET_LICENSES.md`)를 쓴다. 새로 받는 자료는 없다.
- 용량 예상: 홀 껍데기는 가벼워서(삼각형 약 1천 개) 첫 로딩에는 영향이 거의 없다. 그림 파일이 용량을 정한다. 홀 안으로 들어갈 때 받는다(지금 장비 모양을 받는 방식과 같음).
- 낮은 화질(모바일, 저사양)에서는 지금처럼 랙 60기 모델을 자동으로 받지 않고, 상자 랙에 같은 바닥, 벽, 천장을 두른다.
- 조명: 천장 조명 패널은 빛나는 면으로만 그리고 광원은 몇 개만 둔다(그림자와 반사 비용 때문). 외관처럼 정적 그림자를 쓴다.

### 9.3 메뉴 구성(최종)

| 위치 | 메뉴 | 안에 있는 것 |
|---|---|---|
| 왼쪽 아이콘 줄(PC), 아래 줄(모바일) | 모니터링 | 요약, 장비, 알람 (시뮬레이션이 꺼져도 보임) |

## 10. CCTV 메뉴 설계 (가상)

- 목적: 시설의 각 내부 구역에 설치된 **가상** CCTV 화면을 본다. 시뮬레이션 상황(알람, 온도 변화)을 눈으로 확인하는 보조 수단이다.
- **모든 화면은 3D 장면에서 만든 가상 영상이다. 실제 영상, 사람, 얼굴, 차량 번호를 쓰지 않는다.** 화면마다 "가상 CCTV" 글자를 항상 보인다.

### 10.1 카메라 목록(안)

| 번호 | 이름 | 위치와 방향 |
|---|---|---|
| CAM-01 | 출입구 | 홀 입구에서 홀 안쪽을 향함 |
| CAM-02 | 줄 1·2 통로 | 두 줄 사이 통로 끝에서 안쪽을 향함 |
| CAM-03 | 줄 3·4 통로 | 위와 같음 |
| CAM-04 | 줄 5·6 통로 | 위와 같음 |
| CAM-05 | 냉각 구역 서쪽 | CRAC 앞쪽(서쪽 벽) |
| CAM-06 | 냉각 구역 동쪽 | CRAC 앞쪽(동쪽 벽) |
| CAM-07 | 홀 전체(천장) | 천장 모서리에서 아래로 넓게 |
| CAM-08 | 건물 외부 정면 | 외관 카메라(주변 도시 포함) |

위치는 홀 크기(11.0 m x 13.6 m x 4.0 m)와 랙 배치(`hall01.config.json`)에서 계산해 두고, 숫자를 직접 적어 두지 않는다(랙을 옮기면 같이 바뀌게).

### 10.2 화면 구성

- 한 화면에 4분할(2 x 2)로 시작한다. 카메라를 누르면 크게 보고 나머지는 작은 띠로 내려간다.
- 각 화면: 카메라 이름, 현재 시각(시뮬레이션 시각), "가상 CCTV" 표시. 가벼운 영상 효과(약한 잡음, 어두운 모서리)를 더하되 끌 수 있다.
- 알람이 난 랙이 있는 구역의 화면은 빨간 테두리와 알람 이름을 보인다(누르면 그 카메라를 크게). 시뮬레이션이 켜져 있으면 CCTV 화면에도 온도 색을 겹쳐 볼 수 있다(기본은 꺼짐).
- 모바일: 화면 하나씩 가로로 넘기고, 아래에 작은 목록.

### 10.3 구현 방식과 비용

- 화면을 따로 여러 개 만들면 장면을 여러 번 올려야 하므로, **한 개의 3D 화면 안에서 여러 시점을 칸을 나눠 그린다**(가위 영역을 쓰는 방식). 장면 자료는 한 벌만 쓴다.
- 현재 구조는 카메라 하나만 가정한다(`HallScene`). 시점 여러 개를 그리는 부분은 새로 짜야 한다.
- 비용은 칸 수에 비례한다. 낮은 화질에서는 한 번에 최대 2칸, 갱신 속도 5~10프레임으로 줄인다. 고화질은 4칸 15프레임을 목표로 한다(실제 기기에서 측정해 확정).
- CCTV 화면에 보이는 것은 지금 장면에 있는 것(랙, CRAC, 껍데기, 선택한 표시 층)이다. 장면에 없는 사람이나 장비는 그리지 않는다.

사용 목적 ② 이상 대비, ③ 전력 감축을 화면에서 확인하는 부분이다. **모든 값은 간이 모델의 시각화 목적이며 실제 절감량이나 공학적 정확성을 주장하지 않는다.** 화면에도 같은 문구를 보인다.

### 14.1 화면
| 탭 | 내용 |
|---|---|
| 에너지·용량 | 지금 값(IT, 냉각, 설비 전력, PUE, 누적 전력량, 가장 높은 입구 온도), **기준과 비교**("지금을 기준으로 저장" 후 차이와 비율), **공급 온도** 슬라이더(14~27 °C)와 올려 볼 수 있는 폭 힌트, 랙별 여유 전력(적은 순 5기), 줄별 입구 온도 여유와 "과냉각 의심(간이)" |
| 이상 대비 | 시나리오 단추 4개, 시나리오 설명, **대응 순서**(가상 시설 예시), 저장한 기준과의 비교 |

### 14.2 가정 (브라우저 간이 엔진에만 있고 파이썬 생성기에는 없다)
| 가정 | 값 | 이유와 한계 |
|---|---|---|
| 공급 온도 기준 | 18 °C(`t_supply_ref`) | 기본 설정값. 이 값에서는 기존 계산이 그대로다(파이썬과의 값 비교 시험이 계속 통과) |
| 냉각 전력 배수 | 공급 온도 1 °C 올릴 때 3% 감소(`cooling_gain_per_c`), 범위 0.6~1.3 | **실측이나 출처가 있는 값이 아니다.** 줄어드는 방향을 보이려고 정한 값이다. 실제는 설비 종류와 외기 조건에 따라 크게 다르다 |
| 입구 온도 | 공급 온도와 같은 폭으로 움직임 | 기존 L0 모델의 목표 온도 식이 `t_supply`를 그대로 더한다 |
| 랙 정격 전력 | 10 kW(`RATED_KW`) | 엔진의 기준 전력(`power_ref`)과 같게 둠. 여유 전력은 정격 - 지금 값 |
| 과냉각 의심 | 줄의 가장 높은 입구 온도가 주의 기준(27 °C)보다 6 °C 이상 낮음 | 간이 기준이며 힌트용 |
| 올려 볼 수 있는 폭 | 주의 기준 - 가장 높은 입구 온도 - 1.5 °C(안전 여유), 냉각 장치 공급 온도 주의 기준(22 °C)까지로 제한 | 공급 온도를 22 °C 넘게 올리면 냉각 장치 공급 온도 알람이 난다. 이 기준이 입구 온도보다 먼저 걸린다 |

### 14.3 동작 규칙
- 공급 온도 조작은 직접 시뮬레이션에서만 된다(로컬 서버 모드는 슬라이더를 숨김). 시나리오를 다시 시작하면 처음 값(18 °C)으로 돌아간다.
- 조작 기록에 "공급 온도 → N °C"가 남는다.
- 대응 순서는 시나리오 4개(정상, 팬 이상, 냉각 장치 고장, 전력 급증)마다 있고, 실제 운영 절차가 아니라 이 가상 시설의 예시다.

### 14.4 확인한 것과 못 한 것
- 단위 시험 178개(공급 온도 올리면 냉각 전력 12% 줄고 IT 전력 같음, 입구 온도가 같은 방향으로 오름, 기준 비교 계산, 여유 전력, 과냉각 판정), 화면 확인 104개.
- **못 한 것**: 실제 장비나 외부 해석 결과와의 비교(하지 않음, 할 수 없음), 3% 값의 근거 확보.

## 15. 화면 구조 재설계: 계층 나누기 (2026-11-04, 전수조사 결과)

목적: 시뮬레이션과 CCTV 단추가 동시에 눌리는 문제, 패널 글자가 배경과 같은 색이 되는 문제를 근본부터 막는다. 상태: 채택(구현함).

### 15.1 전수조사에서 찾은 것
| 문제 | 원인 | 고친 방법 |
|---|---|---|
| 시뮬레이션과 CCTV가 동시에 눌린 모양 | CCTV 단추가 `data-mode` 흐름과 따로 켜지고 꺼졌다. "지금 어느 화면인가"를 아는 곳이 없어 단추마다 제 마음대로 눌림을 정했다. | 눌림을 한곳(`derive().rail.active`)에서만 정한다. 눌린 단추는 많아야 하나. |
| 모드 표시 글자가 안 보임 | 어두운 테마가 회색 눈금을 뒤집으면서, 글자색으로 쓰던 `--brand-70`이 어두운 파랑이 되어 배경과 비슷했다(대비 3.35). | 글자는 글자 전용 토큰(`--text-brand`)만 쓴다. |
| 알람 개수 글자, 파란 채움 단추 글자가 흐림 | 흰 글자가 얹히는 면의 색이 밝았다(4.18, 3.99). | `--emergency`, `--brand-60`을 어두운 테마에서 진하게 다시 정했다. |
| 상태를 DOM이 들고 있음 | `aria-pressed`, `hidden`을 곳곳(`setMode`, `setControlMode`, `setHeat`, `setStage`, MutationObserver, main.js)에서 따로 바꿔 서로 어긋날 수 있었다. | 아래 계층으로 모았다. |

### 15.2 계층 (위가 아래를 부른다. 아래는 위를 모른다)
1. **화면 조각** (`index.html`, `style.css`, `theme.css`): 그리기만 한다. 스스로 켜고 끄지 않는다.
2. **화면 반영** (`ui.js`의 `apply(vm, ws)`): 계산된 값을 DOM에 한 번에 적용한다. 단추 눌림과 보임은 여기서만 바꾼다.
3. **작업 공간 상태** (`workspace.js`, DOM과 3D를 모르는 순수 함수): `reduce`가 규칙을 지키며 다음 상태를 만들고 `derive`가 화면 값을 계산한다. 단위 시험 11개.
4. **동작 연결** (`main.js`의 `dispatch`): 상태가 바뀐 결과로 3D(온도 색칠), CCTV 열고 닫기, 데이터 출처를 맞춘다. 모든 화면 전환은 `dispatch` 하나로 지난다.
5. **데이터 출처** (`store`, 녹화, 시뮬레이션, 서버): 값을 만든다. 화면 상태를 모른다.

상태는 `{ stage, mode, control, overlay, heat, timeline }` 여섯 가지다. 규칙은 `reduce` 한곳에만 있다: 눌린 메뉴는 하나, CCTV는 서버실 안에서만 열림, 외관으로 나가면 닫힘, 시뮬레이션에 들어가면 온도 색칠 켬, CCTV 중에는 3D 위 도구가 숨음.
다른 방법: 상태 라이브러리(Redux 등)를 들이는 안은 상태가 여섯 개뿐이라 과하다고 보고 버렸다. 함수 두 개로 충분하고 시험하기 쉽다.

### 15.3 글자색 점검 도구
`npm run check:contrast`(`tools/contrast_check.mjs`)가 PC와 휴대폰 폭에서 외관, 모니터링, 패널 탭 각각, 랙 선택, 시뮬레이션 탭 3개, CCTV, 도움말, 서버 연결 대화상자, 마우스를 올린 단추 약 50개를 돌며 보이는 글자의 대비(일반 4.5, 큰 글자 3)를 잰다. 입력칸과 선택 상자, 안내 글자도 본다. 현재 결과: 30개 상태에서 낮은 대비 0종.
한계: 3D 화면 위에 바로 놓인 글자는 배경을 알 수 없어 어두운 장면(#0d1117)으로 가정한다. 사진처럼 밝은 하늘 위의 글자는 이 도구가 잡지 못한다. 눌림, 포커스 상태의 일부는 재지 않는다.
메뉴 규칙은 `npm run check:ui`의 MENU 시험 5개가 지킨다.

### 15.4 남은 구조 일
- `ui.js`의 `bind()`는 아직 단추 눌림을 `aria-pressed` 읽기로 알아내는 곳이 몇 군데 있다(이름 표시, 장비 모양, 공기 흐름). 상태 여섯 가지 밖의 보기 값이라 이번에는 옮기지 않았다.
- `style.css` 끝에 덧붙인 규칙(이어 쓰기)은 파일 나누기(layout, components, theme)로 정리하면 순서에 기대는 부분이 줄어든다.

### 16.3 보여 주려는 흐름과의 대응

### 16.4 아직 남은 구조 문제(이번에 고치지 않음)
- `scene.js`(938줄), `ui.js`(576줄)가 크다. (`main.js`의 데이터 출처 전환은 16.5에서 어댑터로 나눴다.)
- 모니터링의 값 출처는 아직 미리 만든 기록이다. 실제 센서 연결(게이트웨이)은 주소 매개변수로만 붙는다.
- 녹화의 보정 모델(L2) 값은 모니터링에만 있고 시뮬레이션에는 없다(시뮬레이션은 간이 모델 L0만 쓴다). 화면에 "기록 값"과 "계산 값"이 섞이지 않게 모드 표시로 구분하고 있다.
- 실제 휴대폰, Firefox, Safari 확인은 못 했다.

### 16.5 데이터 출처 어댑터 (2026-11-04, 구현함)
문제: 녹화, 시뮬레이션, 라이브/서버 세 출처를 `main.js`의 `startRecording`, `startSim`, `startLive`가 각자 `state`를 직접 바꾸며 처리했다. 화면 갱신 코드(모드 표시, 패널, 시나리오 카드, 시간 막대)가 출처마다 한 벌씩 세 벌이었고, `state.mode`, `server`, `player`, `live`가 서로 어긋날 수 있었다.
결정: `src/sources.js`에 출처 어댑터 세 개(`RecSource`, `SimSource`, `LiveSource`)를 두고 같은 모양으로 맞춘다. 어댑터는 화면을 모른다.
- 공통: `kind`, `control`, `player`, `open(args)`, `close()`, `advance(dt)`(화면을 다시 그려야 하면 true), `describe()`(모드 표시, 패널, 시나리오, 카드, 시간 막대), `statusText()`, `send(c)`.
- `main.js`는 `useSource(source, args)` 한 경로로 출처를 바꾸고 `present(source)` 한 벌로 화면을 맞춘다. 프레임 루프는 `source.advance(dt)` 하나만 부른다.
- 기존 코드가 읽는 `state.mode`, `state.player`, `state.sim`, `state.live`, `state.server`는 지금 출처에서 읽는 값(getter)이라 같은 이름으로 동작한다.
- 동작이 바뀐 곳 한 가지: 시뮬레이션에서 모니터링으로 돌아오면 재생 설정(반복, 속도, 일시정지)을 시뮬레이션에서 물려받던 것을 새로 시작하도록 고쳤다(녹화가 끝에서 멈추던 문제). 같은 녹화 안에서 시나리오를 바꿀 때는 이어 간다.
확인: 단위 시험 14개(가짜 클라이언트 포함), 화면 시험 116개(모의 게이트웨이로 로컬 서버 연결, 값 표시, 조작 전달, 모니터링 복귀 후 연결 해제까지 확인).
다른 방법: 출처마다 클래스 상속을 두는 안은 세 출처의 차이(시간이 있는가, 조작을 보내는가)가 커서 공통 부모의 이점이 작다고 보고, 같은 모양만 맞추는 방식으로 했다.

### 16.6 미리 계산한 시뮬레이션 모음과 메뉴 개편 (2026-11-04, 사용자 결정)
결정(사용자): "기본 상태와 시나리오의 시뮬레이션 값은 미리 뽑아 보여 주고, 서버에 직접 연결해 상세 시뮬레이션을 하게 한다." 브라우저 간이 계산은 "간이"로 낮춰 남긴다. 미리 뽑는 범위는 이상 상황 4개 + 급기 온도 5단 + 부하 3단(이름이 겹치는 18도와 100%는 정상 가동 녹화를 가리켜 용량을 두 번 쓰지 않는다).

메뉴: 모니터링(기록) / **시뮬레이션**(미리 계산한 값 12개) / **간이 계산**(브라우저 L0, 슬라이더) / CCTV. 시뮬레이션 메뉴에는 조작 탭이 없고 에너지·용량, 이상 대비 탭이 있으며, "상세 시뮬레이션은 서버에 연결" 안내가 보인다. 시나리오 목록은 그룹(이상 상황, 급기 온도, 부하)으로 묶인다. 비교는 에너지 탭의 "기준으로 저장"으로 한다(예: 급기 18도 저장 후 24도 선택 → 냉각 전력 −18.0%).

**계산을 고친 곳(미리 계산한 값이 틀리지 않으려고)**
- Warp 열 계산(`hall60_sim.py`)이 급기 온도를 모듈 상수 18도로 고정해 쓰고 있었다. L1에서 `t_supply`는 공급 온도 센서 값에만 쓰였으므로, 그대로 급기별 녹화를 뽑으면 **온도는 그대로이고 숫자만 다른 값**이 나왔을 것이다. `Sim`이 급기 온도를 받게 했다. 식이 온도에 대해 선형이라 급기를 올리면 온도장 전체가 같은 폭으로 오른다(시험: 24도 − 18도 = 평균 +6.00, 어느 칸도 0.2 이상 벗어나지 않음). 기본 18도의 결과는 바뀌지 않는다(시험: 같음).
- 보정 모델(L2)은 18도에서 배웠다. 급기가 다르면 L1 값에서 차이만큼 빼서 넣고 결과에 다시 더한다(선형 가정). 이 가정은 18도 밖에서 검증하지 않았다.
- 냉각 전력이 급기에 따라 변하도록 파이썬 생성기에도 웹 간이 계산과 같은 가정(1도당 3%, 0.6~1.3배)을 넣었다. **실측이 아닌 가정**이다. 기본 18도에서는 1배라 기존 값과 같다(변경 전 코드와 같은 명령으로 만든 녹화를 비교: 차이 0).

**값(300초 마지막 시각)**
| 상태 | IT kW | 냉각 kW | 설비 kW | PUE | 가장 높은 입구 °C | 알람 |
|---|---|---|---|---|---|---|
| 급기 16 | 440 | 33.9 | 500 | 1.137 | 17.6 | 0 |
| 급기 18(기준) | 440 | 32.0 | 498 | 1.133 | 19.5 | 0 |
| 급기 20 | 440 | 30.1 | 496 | 1.128 | 21.6 | 0 |
| 급기 22 | 440 | 28.2 | 494 | 1.124 | 23.6 | 8 |
| 급기 24 | 440 | 26.2 | 492 | 1.120 | 25.6 | 8 |
| 부하 70% | 308 | 32.0 | 358 | 1.164 | 18.3 | 0 |
| 부하 100%(기준) | 440 | 32.0 | 498 | 1.133 | 19.5 | 0 |
| 부하 130% | 571 | 32.0 | 638 | 1.116 | 19.6 | 79 |

**한계(정직하게)**
- **냉각 전력은 부하와 무관하다**(CRAC 팬 전력과 기본 소비만 더한 합성 추정). 현실에서는 부하가 늘면 냉각 전력도 는다. 그래서 부하가 늘수록 PUE가 낮아지는데, 이는 이 모델의 한계가 만든 방향이다.
- 부하 130%에서 가장 높은 입구 온도가 거의 오르지 않는다(19.5 → 19.6). Warp 모델이 통로 급기를 충분히 받는 상태에서 전력에 둔감하다. 부하 130%의 알람 79건은 랙 전력 주의 기준(10 kW)에서 나온다.
- 급기 22도 이상의 알람 8건은 냉각 장치 공급 온도 주의 기준(22도)에서 나온다(입구 온도는 아직 27도 아래).
- 급기별 입구 온도는 정확히 급기 변화만큼 오른다(선형 가정의 결과). 실제로는 비선형일 수 있다.
- **모델 버전이 섞여 있다(해결하지 않음):** 기존 이벤트 녹화 4개는 보정 모델 파일(`model.pkl`, 10월 27일)이 갱신되기 전에 만들었다. 현재 모델로 다시 만들면 알람 목록은 같지만 값이 최대 1.59도(팬 이상), 신뢰 등급이 달라진다(`fan_fault` 마지막 시각 **ok 48, low 12 → ok 48, caution 9, low 3**). 이 숫자는 Unreal 연결 확인과 문서 5곳(docs/12, 18, 20, ADR-011, E5)에 쓰였으므로 조용히 바꾸지 않고 기존 녹화를 유지했다. 새 6개는 현재 모델이라 정상 가동과의 값 차이가 최대 0.04도 섞인다. 이벤트 녹화를 다시 만들지, 문서의 숫자를 고칠지는 **사용자 결정 사항**이다.
- 서버가 받는 조작에는 급기 온도가 아직 없다(다음 단계).

### 16.7 시뮬레이션 서버와 서버 데이터 (2026-11-04, 사용자 결정)
결정(사용자): "시뮬레이션 모델이나 프레임 저하가 일어날 수 있는 부분은 서버에서 진행하고, 서버는 저장소에 두고, 화면은 서버에서 필요한 데이터를 받아 쓴다." 범위는 **시뮬레이션 계산 + 데이터 제공**으로 정했다(CCTV 화면을 서버에서 그려 영상으로 보내는 안은 이번에 하지 않았다: GPU 서버와 지연, 구현 규모가 커서 첫 단계에서 제외). 서버 위치는 **저장소에 코드와 실행 구성을 두는 것**(클라우드 배포와 외부 노출은 하지 않았다).

**한 일**
- `server/`: README(실행 3가지, 안전, 밖에 열기), `run_local.ps1`, Dockerfile, compose, 매니페스트 사본.
- 서버(`serve.py`)에 급기 온도 조작(`supply_temp`, 14~27도)을 추가했다. 모델(L0, L1 Warp, L2)과 냉각 전력 집계가 다음 단계부터 새 값을 쓰고, 시나리오를 다시 시작하면 처음 값으로 돌아간다. 서버가 알려 주는 상태(snapshot의 `controls.supply`, 조작 사건)로 화면 슬라이더가 맞춰진다.
- 같은 포트에서 HTTP 데이터 API를 준다(`api.py`): `/healthz`, `/api/meta`, `/api/library`, `/api/library/<id>`. 읽기 전용, 목록에 있는 id만 열고, 허용한 출처에만 CORS 머리글, 압축, 초당 요청 제한.
- 웹: `src/server_data.js`가 서버 연결 주소에서 데이터 API 주소를 만들고 목록과 녹화를 받는다. 목록은 형식을 검사해서 틀리면 쓰지 않는다. 실패하면 사이트에 포함된 파일로 돌아가고(대체 경로), 시뮬레이션 메뉴에 출처가 보인다("서버(주소)에서 받음" 또는 "이 사이트에 포함된 파일"). 서버 모드에서도 공급 온도 슬라이더가 열린다.
- CSP(`connect-src`)에 `http://127.0.0.1:*`, `http://localhost:*`, `https:`를 더했다. 서버 연결 주소 규칙(`checkLiveUrl`: 암호화하지 않은 `ws://`는 이 컴퓨터만, 그 밖은 `wss://`)과 같은 범위다. `https:` 전체를 연 것은 기존의 `wss:` 전체 허용과 같은 수준의 완화다.

**확인한 것**
- 파이썬 시험 103개(API 23, 급기 조작 3, 서버 구성 파일 9 포함), 웹 단위 시험 228개, 화면 시험 127개(모의 서버: 서버 데이터 사용, 공급 온도 조작 전달, API 없는 서버에서 대체 경로).
- **실제 GPU 서버(L2)와 실제 웹 화면을 연결해 확인했다**: 서버가 알려 준 급기 24도로 슬라이더가 맞춰지고, 22로 바꾸면 냉각 전력이 28.16 kW가 됐다(미리 계산한 급기 22도 값과 같음). 시뮬레이션 메뉴의 목록 12개와 녹화를 서버에서 받았다. 데이터 API 응답은 목록 927 B(압축), 녹화 146 KB(압축). 경로 탈출 시도는 404, 허용하지 않은 출처에는 CORS 머리글이 없었다.
- `run_local.ps1`로 L0와 L2 서버가 뜨는 것을 확인했다.

**확인하지 못한 것과 한계**
- **Docker 이미지는 빌드도 실행도 못 했다.** 이 컴퓨터에 Docker가 없다. 경로, 명령, 사본의 일치만 시험이 본다(`test_server_files.py`). 처음 빌드하면 고칠 곳이 나올 수 있다.
- 서버는 인증이 없다. 출처(Origin) 확인은 브라우저에만 효과가 있고, 브라우저가 아닌 도구는 조작을 보낼 수 있다. 밖에 열려면 TLS와 인증을 걸어 주는 앞단이 필요하며 이 저장소는 그 구성을 주지 않는다.
- 서버 상태는 접속한 모든 화면이 함께 쓴다(한 화면의 조작이 다른 화면에 보인다).
- 서버 L1 모드에서 급기를 바꾸면 공기가 새 온도로 서서히 바뀐다(보정 모델 L2는 선형 가정으로 18도 기준에서 배운 값을 옮겨 쓴다. 18도 밖에서는 검증하지 않았다).
- CCTV와 3D 그리기는 여전히 브라우저가 한다. 프레임 저하의 가장 큰 원인(여러 칸 렌더)은 서버로 옮기지 않았다.
- 같은 서버를 여러 사람이 공개로 쓰는 시나리오(접속 수 8, 계산 한 벌)는 시험하지 않았다.

### 16.8 외부 솔버 결과 파이프라인 (2026-11-04, 사용자 요청: "리얼 DC 결과도 반영이 되도록 파이프라인 구성만 해 두자")
결정: 상용 CFD 도구(Reality DC 등)나 다른 솔버의 결과를 **VTK로 받아 서버를 거쳐 이 컴퓨터의 화면에서만** 보이게 하는 파이프라인을 구성만 한다([docs/28](28_kit_run_and_commercial_tool_options.md) 방안 C의 구성 부분). 공개 도구(OpenFOAM `foamToVTK`)의 결과도 같은 길로 넣을 수 있다. 사용법과 한계는 [server/README.md "외부 솔버 결과"](../server/README.md).

**구성(`sim/sensors/dct_sensors/external/`)**: 레거시 VTK 읽기(`vtk_legacy.py`), 좌표·단위·축·온도 단위 약속(`mapping.py`), 앵커에서 읽어 녹화 JSON과 자료 묶음 만들기(`pack.py`), 명령줄(`inspect`, `build`, `demo`), 시험용 쓰기(`writer.py`). 앵커 위치는 `server/data/anchors.json`(가상 홀 USD에서 `scripts/export_anchors.py`로 뽑은 사본). 서버는 `--extra-data-dir`로 묶음을 받아 데이터 API 목록에 합친다(같은 id는 기본 자료가 우선).

**결과가 새어 나가지 않게 한 장치**
| 장치 | 내용 |
|---|---|
| 출력 위치 제한 | git이 무시하지 않는 위치는 거절(`ensure_ignored`). 기본 `sim/out/local_only/external_pack/` |
| `.gitignore` | `*.vtk`, `*.vtu`, `*.vti`, `*.room` |
| CI 시험 | 저장소에 그런 파일이 추적되지 않음, 공개 목록과 녹화에 외부 항목이 없음(`external_guard.test.js`, `check_data.mjs`) |
| 화면 | 서버가 줄 때만 보임. 고르면 모드 표시가 "외부 솔버 결과 (도구) · 이 컴퓨터의 서버만 줌"으로 바뀜(우리 모델과 구분) |
| 데모 | 합성 시험 데이터(`demo`)로 흐름을 확인. "실제 계산 결과가 아니다"를 항목 설명에 적음 |

**확인한 것**: 파이썬 시험 37개(VTK 읽기 ASCII/BINARY 4종 데이터셋과 5.1 연결 형식, 오류 메시지, 좌표 변환(mm, 축 뒤집기, 원점, 켈빈), 앵커 값이 장의 값과 맞음, 좌표가 틀리면 힌트와 함께 실패, 알람 규칙, 저장소 보호, 서버 합치기), 웹 단위 시험 4개, 화면 시험 1개(모의 서버), **실제 서버와 실제 웹 화면으로 데모 묶음을 보였다**(그룹 표시, 모드 표시, 값 표시). 전체: 파이썬 140, 웹 단위 233, 화면 128.

**확인하지 못한 것(중요)**
- **실제 외부 도구의 `.vtk`로는 시험하지 못했다**(이 저장소에 그런 파일이 없고, 올리지도 않는다). 문서(NVIDIA Kit 확장 설명)로 `.vtk`를 내보낸다는 것만 확인했다. 실제 파일의 구조(데이터셋 종류, 값 이름, 단위, 좌표 원점)가 가정과 다르면 읽기나 mapping을 고쳐야 한다. 앞단에서 `inspect`가 구조를 보여 주고, 맞지 않으면 이유와 함께 거절한다.
- 상용 도구 결과를 개인 포트폴리오 용도로 계산해도 되는지(라이선스, 회사 규정)는 판단하지 않았다. 이 구성은 "올리지 않는다"만 지킨다.
- 외부 결과는 정상 상태 한 장면이다(시간 변화 없음). 비정렬 값은 가장 가까운 점 값을 쓴다(보간 없음). 3D 온도장 자체(부피 데이터)를 화면에 그리는 것은 하지 않았다(앵커 값만).
