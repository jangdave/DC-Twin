# 30. 아키텍처 검토: 문제 진단 (2026-11-04)

- 상태: 초안. 일부는 같은 날 고쳤고(7절), 사용자가 정할 것(6절)은 2026-11-12에 정했다. 나머지 계획 항목은 남아 있다.
- 목적: 구조, 기능 연결, 데이터, 모델, 서버 안전, 시험과 배포 과정에서 **확인된 문제**를 심각도 순으로 모으고, 무엇을 고쳤고 무엇이 남았는지 밝힌다.
- 읽는 사람: 이 프로젝트의 소유자, 인수인계를 받는 개발자.
- 관련: [docs/27](27_web_ui_redesign_plan.md) 15~16장(웹 화면 구조), [server/README.md](../server/README.md), [docs/29](29_server_side_rendering_review.md).

## 1. 검토 방법과 신뢰도
1. **독립 검토 둘**: 이 작업의 제 결론을 알려 주지 않은 새 검토자 둘이 읽기 전용으로 점검했다. 하나는 웹 화면 코드(`web/viewer`), 다른 하나는 시스템 전체(`sim`, `experiments`, `server`, `gateway`, 데이터 흐름, CI, 문서)다.
2. **제 검증**: 검토자의 보고는 모델이 쓴 것이라, 심각도가 높은 주장은 제가 코드와 실행으로 다시 확인했다(아래 "확인" 열). 확인하지 못한 항목은 "미확인"으로 남겼다.
3. **제 측정**: 같은 날 직접 잰 것(부하와 냉각 전력, 보정 모델의 범위 밖 비율, Docker 실행, 실제 서버와 화면 연결)을 더했다.

한계: 검토자 둘 다 GPU 실행(L1, L2), 실제 센서(MQTT), Unreal은 점검하지 못했다. 브라우저 안의 프레임 속도와 메모리는 측정하지 않았다.

## 4. 유지할 좋은 점 (고치다가 깨지 않게)
1. **서버 입력 검증 층**: `messages.js`가 서버 JSON을 형식, 범위, 길이, 허용 목록으로 걸러 `null`을 돌려주고 센다. `innerHTML`은 `src/` 전체에 0건이라 XSS 면이 거의 없다.
2. **의존 방향이 단방향**이고 출처를 같은 모양의 어댑터(`player`, `describe`)로 갈아 끼운다. 이것이 시험 가능성을 만든다.
3. **알람 규칙을 파이썬과 JS와 게이트웨이가 한 파일(`alarm_vectors.json`)로 함께 시험한다.** 이 방식을 집계식에도 넓히는 것이 M1의 해법이다.
4. **서버 기본값이 안전하다**: loopback만, 밖으로는 토큰 필수, 첫 메시지 인증, 상수 시간 비교, 인증 전 값 없음, 조작은 종류·대상·범위 검증, 데이터 API는 경로를 받지 않고 목록의 id만 연다. Docker는 비루트, 읽기 전용, 권한 제거.
5. **보정 모델이 범위를 벗어나면 `fallback` 등급을 내고** 구간과 신뢰 등급을 값과 함께 보낸다(그래서 H3의 빈틈이 숨지 않고 드러났다).
6. **시뮬레이션 입력을 장면 USD에서 읽고** 장면은 설정에서만 만들며, 외부 솔버 결과는 gitignore된 위치에만 쓰고 CI가 새어 나갔는지 시험한다.
