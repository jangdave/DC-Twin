# 29. 3D 그리기를 서버로 옮기는 안 검토

- 상태: **초안** (2026-11-04)
- 목적: 웹 보기 화면의 3D 그리기(특히 CCTV 여러 칸)를 브라우저에서 서버로 옮기면 무엇을 얻고 무엇을 잃는지 비교하고, 지금 할 일과 나중에 정할 일을 나눈다.
- 읽는 사람: 이 프로젝트의 소유자(결정할 사람), 인수인계를 받는 개발자.
- 관련: [ADR-004](decisions/ADR-004-streaming-hosting.md)(호스팅), [ADR-011](decisions/ADR-011-webgl-viewer.md)(웹 보기 화면), [12](12_unreal_design.md) 7장(Pixel Streaming), [13](13_omniverse_research.md), [27](27_web_ui_redesign_plan.md) 10장(CCTV)·16.7(서버), `experiments/results/E0_omniverse_capability_probe.md` 2.5장(ovrtx)
- 주의: 모든 영상과 수치는 **시각화 목적**이다. 공학적 정확성을 주장하지 않는다. 아래 측정은 이 컴퓨터 한 대에서 한 것이며, 다른 기기나 네트워크의 값이 아니다.

## 1. 한 줄 결론

**지금은 E(서버 없이 브라우저 비용 줄이기)를 먼저 하고, D(브라우저가 주 화면을 그리고 서버는 특별한 화면만 그림)는 "GPU 서버가 생기고 인증이 붙은 뒤"의 선택으로 남긴다.** C(전체 화면을 서버가 그림)는 이 프로젝트에서는 웹 보기 화면을 만든 이유(가볍게 누구나, 설치 없이)를 없애므로 권하지 않는다. Unreal Pixel Streaming은 웹 보기 화면의 대체가 아니라 Unreal 클라이언트의 배포 방식으로 따로 둔다(ADR-004).

## 2. 지금 구조 (사실 확인)

| 항목 | 내용 |
|---|---|
| 3D 그리기 | 브라우저(`web/viewer`, Three.js 0.170, Vite). 장면은 `src/scene.js` |
| CCTV | 가상 카메라 7대. 한 캔버스를 칸으로 나눠(가위 영역과 뷰포트) 최대 4칸을 그림. `src/cctv.js`, `src/cctv_ui.js`, `scene.js`의 `_renderCctv` |
| 칸 수와 속도 | 낮음 2칸 8프레임/초, 보통 4칸 12, 높음 4칸 15. **모두 실제 기기 측정 전의 시작값**(`CCTV_LIMITS`) |
| 서버 | `sim/sensors/dct_sensors/serve.py`: 시뮬레이션 계산, 웹소켓과 HTTP 데이터 API. 그리기는 하지 않음. **접근 토큰 인증이 있다**(WebSocket은 첫 메시지로 토큰, 시작 규칙 포함. docs/27 16.9). 설명은 `server/README.md` |

| 이 컴퓨터 | RTX 5090 32GB. 면접 시연용으로는 쓸 수 있으나 상시 서버는 아님(ADR-004) |

프레임 저하의 가장 큰 원인은 "여러 칸을 한 번에 그리는 것"이다([27](27_web_ui_redesign_plan.md) 16.7). 아래 측정 2가 이를 뒷받침한다.

## 3. 측정 (2026-11-04, 이 컴퓨터)

### 3.1 측정 1: 서버에서 그리는 비용 (ovrtx 0.3.0, RTX 5090)

- 스크립트: `experiments/omniverse_probe/bench_ovrtx_frames.py` (새로 만듦). 결과: `out/bench_ovrtx_frames.json`, 미리보기 `out/bench_ovrtx_frame_*.jpg`(git 제외).
- 방법: 홀 장면 `usd/scenes/hall01.usda`(랙 60기, CRAC, 껍데기 포함)를 그대로 열고, 바닥 위 조명 2개와 카메라 1대를 덧씌웠다. 워밍업 15프레임 뒤 60프레임을 그렸다. 이를 **같은 프로세스에서 3번 반복**했다. 프레임마다 (a) 그리기 `step`, (b) 색상 결과를 CPU로 복사, (c) 5프레임마다 JPEG/WebP 인코딩 시간과 크기를 쟀다.
- 렌더러 만들기 3.3초, 장면 열기 0.05초.

| 해상도 | 그리기 step 중앙값 (3번의 범위) | step 최솟값 | CPU 복사 중앙값 | 합계(그리기+복사) |
|---|---|---|---|---|
| 640 x 360 | 5.6 ~ 6.6 ms | 2.6 ~ 3.5 ms | 2.1 ~ 2.5 ms | 약 8 ~ 9 ms |
| 1280 x 720 | 5.7 ~ 6.1 ms | 2.4 ~ 3.7 ms | 9.5 ~ 9.8 ms | 약 15 ~ 16 ms |

| 해상도 | JPEG(품질 75) 크기 | JPEG 인코딩 | WebP(품질 75) 크기 | WebP 인코딩(PIL, CPU) |
|---|---|---|---|---|
| 640 x 360 | 12.2 ~ 12.8 KB | 약 0.5 ms | 3.8 ~ 4.1 KB | 18 ~ 23 ms |
| 1280 x 720 | 34.3 ~ 35.8 KB | 약 1.7 ms | 8.6 ~ 9.3 KB | 71 ~ 75 ms |

한 번 틀어 두면 가끔 step이 40~200 ms로 튀는 프레임이 있었다(최대 209 ms). 이 컴퓨터에서 다른 작업이 GPU를 같이 쓸 수 있다.

**전송량 추정** (프레임 크기 x 칸 수 x 초당 프레임. 칸당 영상이 따로 온다고 가정, 640 x 360 칸):

| 칸 수와 속도 | JPEG | WebP |
|---|---|---|
| 2칸, 8프레임/초 | 약 1.6 Mbps | 약 0.5 Mbps |
| 4칸, 12프레임/초 | 약 4.8 Mbps | 약 1.5 Mbps |
| 4칸, 15프레임/초 | 약 6.0 Mbps | 약 1.9 Mbps |

1280 x 720 칸이면 JPEG는 위 값의 약 2.8배(2칸 8프레임 4.5 Mbps, 4칸 15프레임 16.8 Mbps), WebP는 약 2.3배다. 한 사람이 보는 동안의 값이다. 보는 사람이 늘면 그만큼 곱해진다(같은 카메라를 여럿이 보면 한 번 그려 나눠 보낼 수 있다).

**이 숫자를 믿을 때의 한계 (중요)**
- 그린 장면이 **어둡고 단순하다.** 조명을 직접 맞추지 않았고(카메라가 가림막 지붕 위쪽에서 보는 각도가 되어 통로가 잘 안 보임), 영상이 대부분 검다. 그래서 **JPEG/WebP 크기는 실제 CCTV 화면보다 작게 나왔을 가능성이 크다**(밝고 복잡한 화면이면 몇 배 클 수 있다). 시간도 조명이 복잡하면 늘 수 있다.
- 장면 안의 **온도 색, 알람 표시는 들어 있지 않다.** 서버에서 그리면 이 값을 USD 속성으로 매 프레임 바꿔 넣어야 하는데 **그 비용은 재지 않았다.**
- `step`이 GPU 작업이 끝날 때까지 기다리는지 확인하지 못했다. CPU 복사 시간이 포함된 합계를 "프레임당 비용"으로 보는 것이 안전하다.
- 카메라 1대, 프로세스 1개 기준이다. **여러 카메라, 여러 프로세스, 여러 사람의 동시 접속은 재지 않았다.**
- H.264 같은 영상 인코딩, 웹소켓/WebRTC 전송, 네트워크 지연, Kit 방식(Kit headless)은 재지 않았다. WebP 인코딩 시간은 PIL(CPU)이라 GPU 인코딩과 다르다.

**동시 접속 거칠게 계산해 보기** (재지 않은 가정 위의 어림값): 640 x 360 한 칸이 8.5 ms이면, 4칸 12프레임/초는 1초에 약 0.4초의 GPU 시간이 든다. 이 값만 보면 GPU 한 장에 **2명 안팎**이다(칸을 서로 공유하지 않을 때). 같은 7대 카메라를 모두에게 나눠 보내면(12프레임/초, 7대 = 약 0.7초) 접속자 수보다 **전송량**이 한계가 된다. 실제 값은 위 한계 때문에 달라질 수 있다.

### 3.2 측정 2: 브라우저에서 칸 수에 따른 비용 (상대 비교만)

- 방법: `web/viewer`의 빌드 결과를 Edge(`--use-angle=swiftshader`)로 열고, 서버실에서 CCTV를 켠 뒤 `scene._renderCctv`를 속도 제한 없이 12번 부르고, 부른 직후 `readPixels` 1픽셀로 그리기가 끝나기를 기다려 `performance.now()`로 쟀다(앞 2번 제외, 3번 반복). 스크립트는 저장소에 넣지 않았다(임시 파일).
- **이것은 소프트웨어 그리기(SwiftShader)다. 실제 기기의 프레임 속도가 아니다.** 의미 있는 것은 **1칸과 4칸의 비율**뿐이다.

| 상태 | 칸 크기 | 전체 픽셀 | 한 번 그리는 시간 (3번의 중앙값) |
|---|---|---|---|
| 4칸 | 478 x 349 x 4 | 약 667,000 | 185 ~ 195 ms |
| 1칸(칸을 눌러 크게) | 964 x 707 x 1 | 약 682,000 | 49.5 ~ 50.9 ms |

전체 픽셀 수가 거의 같은데 4칸이 **약 3.7 ~ 3.9배** 걸렸다. 즉 이 환경에서는 비용이 화면 크기보다 **칸 수(장면을 다시 그리는 횟수)에 비례**한다. 실제 GPU에서도 같은 경향이 나올지는 **기기에서 재야 안다**(GPU가 빠르면 그리기 호출 수 비용이 더 두드러질 수도 있고, 덜할 수도 있다).

## 4. 선택지

### A. 지금 그대로 (브라우저에서 그림)

- **동작**: 변경 없음. `scene.js` `_renderCctv`가 한 캔버스에서 칸을 나눠 그림.
- **장점**: 정적 사이트(GitHub Pages)로 배포되고 서버 비용이 0이다. 오프라인에서도 동작. 랙 클릭 선택과 터치가 장면과 바로 이어진다. 이미 구현과 시험(화면 확인 127개)이 있다.
- **단점**: 저사양 기기에서 4칸이 무거울 수 있다(측정 2의 비율이 근거. 실제 기기 값은 없음). 시작값(2/4/4칸, 8/12/15)이 맞는지 모른다.
- **비용**: GPU 서버 0, 전송량 0(장면 자료 한 번 받음), 지연 0.
- **동시 접속**: 사용자 기기가 각자 그린다. 접속자 수와 무관.
- **보안**: 서버가 필요 없으므로 새로 생기는 위험 없음.
- **오프라인과 대체**: 가장 좋다.
- **작업량**: 없음. 대신 실제 기기 측정이 필요(작음).
- **잃는 것**: 없음.

### B. 서버가 CCTV 칸만 그림

- **동작**: 서버(ovrtx 또는 Kit headless)가 가상 카메라 7대를 그려 JPEG/WebP/H.264 프레임을 웹소켓이나 WebRTC로 보낸다. 브라우저는 칸에 이미지만 놓는다.
- **바뀌는 곳**: `sim/sensors/dct_sensors/serve.py`(영상 채널 추가) 또는 새 렌더 프로세스, 장면 USD에서 카메라 읽기(`usd/scenes/hall01.usda`에 카메라가 없어 `src/cctv.js`의 계산을 USD로 옮겨야 함), `web/viewer/src/cctv_ui.js`(캔버스 대신 `<img>`/`<video>` 칸), `scene.js`(CCTV 분기 일부 삭제). 온도 색과 알람 테두리는 서버에서 USD 값을 바꿔 그리거나, 브라우저가 겹쳐 그리는 별도 층이 필요.
- **장점**: 브라우저 부담이 가장 큰 부분(여러 칸)이 사라진다. 서버에서 이미 시뮬레이션을 하므로 한 장비에서 같은 장면 상태로 그릴 수 있다. 같은 카메라를 여러 명이 볼 때 한 번만 그릴 수 있다. 품질을 높이기 쉽다(Omniverse 경로 추적 등, 시각화 목적).
- **단점**: GPU 서버가 필요하다. 온도 색을 서버에서 어떻게 그릴지 새로 짜야 한다. 3D 화면과 CCTV 칸의 **외관이 달라질 수 있다**(그리기 방식이 달라서). 지연이 생긴다.
- **비용**: GPU 서버(상시면 비용 큼, ADR-004). 전송량은 3.1의 표(조건부 값): 640 x 360 WebP 4칸 15프레임 약 1.9 Mbps, JPEG 약 6 Mbps. 지연은 **재지 않음**. 동시 접속은 3.1의 어림값(칸을 공유하지 않으면 GPU 한 장에 2명 안팎, 공유하면 전송량이 한계).
- **보안**: 영상 채널이 하나 늘어나고, 서버에 인증이 없으면 누구나 GPU를 쓰게 된다. 인증과 접속 수 제한이 **먼저** 필요하다.
- **오프라인과 대체**: 서버가 없거나 끊기면 CCTV가 없다. 대체로 A의 브라우저 그리기를 남겨 두어야 한다.
- **작업량**: 중간 ~ 큼. 새 렌더 프로세스, 영상 전송, 카메라를 USD로 옮김, 온도 색 처리, 화면 확인 새로 작성.
- **잃는 것**: 정적 사이트만으로는 CCTV가 안 된다(서버 필요). 오프라인 불가. **CCTV 칸의 랙 클릭 선택**은 지금 가능한 것이 아니라(현재 칸 클릭은 "크게 보기") 새로 만들려면 서버가 의미 라벨(semantic) 영상을 같이 받아 와야 한다. ovrtx가 라벨을 주는 것은 확인했다(E0 2.5장).

### C. 서버가 3D 화면 전체를 그림 (Unreal Pixel Streaming 2 또는 Omniverse 스트리밍)

- **동작**: 브라우저는 영상 재생기와 UI만 맡는다. Unreal이면 `unreal/DataCenter_DT`를 서버에서 돌려 WebRTC로 보낸다([12](12_unreal_design.md) 7장). Omniverse면 Kit 앱(`dctwin.base_editor`)의 스트리밍을 쓴다(미시험).
- **바뀌는 곳**: `web/viewer`의 3D 전체(Three.js 장면, 선택, 라벨, 흐름 입자)를 영상 + 메시지 채널로 대체. 사실상 웹 보기 화면을 다시 만드는 일.
- **장점**: 가장 좋은 화질을 낼 수 있고, Unreal 클라이언트와 같은 장면을 쓴다. 기기 성능과 무관하다.
- **단점**: **접속자 한 명마다 GPU 세션 하나**가 든다. Pixel Streaming은 세션당 GPU 렌더링과 영상 인코딩이 필요하다(ADR-004). 이 프로젝트는 GPU 서버가 없다. 입력 지연이 걷는 느낌에 영향([12](12_unreal_design.md) 10.5)이 있고, **모바일 터치는 지원하지 않는다**([12](12_unreal_design.md) 7장).
- **비용**: 접속자 수 만큼의 GPU. 1080p 영상 전송량은 **재지 않음**(E3에서 측정 예정). 지연은 **재지 않음**.
- **보안**: 시그널링 서버(WebRTC 연결을 맺어 주는 서버)를 열어야 한다. 인증과 접근 제한이 필수(ADR-004 검증 목록).
- **오프라인과 대체**: 서버가 없으면 아무것도 안 보인다. 대체가 없다.
- **작업량**: 큼. 웹 보기 화면 전체 재작성, 스트리밍 서버 운영.
- **잃는 것**: 정적 배포, 오프라인, 터치 부드러움, 가벼운 첫 화면(웹 보기 화면을 만든 이유, ADR-011). 면접 시연(본인 PC) 말고는 상시 공개가 어렵다.

### D. 섞기: 브라우저가 주 화면, 서버는 특별한 화면만

- **동작**: 기본은 A. "높은 화질 정지 사진"이나 CCTV 칸만 서버에 요청한다. 서버가 없거나 느리면 자동으로 A로 돌아간다. 화질 단계(낮음/보통/높음)에 "서버 그리기"를 새 단계로 둘 수 있다.
- **바뀌는 곳**: B의 변경 + `web/viewer/src/server_data.js` 비슷한 서버 연결 확인과 전환 로직 + 화질 선택.
- **장점**: 서버가 있는 곳에서는 CCTV가 가볍고, 없는 곳(GitHub Pages만)에서는 그대로 동작한다. 서버 비용을 필요한 만큼만 쓴다. "서버 있으면 더 좋은 화면"이라는 이야기가 포트폴리오에도 맞다(Omniverse 시뮬레이션이 서버에서 이미 돌고 있음).
- **단점**: **두 가지 그리기 경로를 모두 유지**해야 한다(시험과 고치는 일이 두 배). 두 경로의 모양이 달라서 사용자가 이상하게 느낄 수 있다.
- **비용**: B와 같다(서버를 켠 시간만큼). 사용자가 없으면 0.
- **보안**: B와 같다. 인증 전에는 공개로 열지 않는다.
- **오프라인과 대체**: 서버 없음 → 자동으로 A. 오프라인에서 A 그대로 동작.
- **작업량**: 큼(B + 전환 + 두 경로 시험).
- **잃는 것**: 잃는 기능은 거의 없다. 대신 구현과 유지 비용을 얻는다.

### E. 서버 없이 브라우저 비용 줄이기

- **동작**: 화면에 안 보이는 칸은 그리지 않기, 칸이 작을수록 속도를 낮추기, 움직임이 없으면 다시 그리지 않기(이미 `_dirty`가 있음), 기기에 맞춰 칸 수와 프레임을 자동으로 낮추기, 정적 부분 합치기, 칸 해상도를 낮춰 그리고 늘리기(`renderer.setPixelRatio`나 칸별 낮은 해상도), 텍스처와 LOD(멀리 있는 것은 단순하게) 줄이기, 오프스크린 캔버스와 작업자(Worker)에서 그리기.
- **바뀌는 곳**: `src/scene.js`(`_renderCctv`), `src/cctv.js`(`CCTV_LIMITS`), `src/cctv_ui.js`. 작업자 그리기는 `src/main.js`와 `scene.js` 구조를 크게 바꿔야 한다.
- **장점**: 서버, 비용, 보안 변화가 없다. 정적 배포와 오프라인이 그대로다. 측정 2에서 비용이 **칸 수에 비례**했으므로 "칸 수와 갱신 간격을 줄이는 것"이 효과가 곧바로 나올 가능성이 높다.
- **단점**: 아주 저사양 기기에서는 한계가 있다. 화질을 낮추는 것이라 서버만큼 좋아지지는 않는다. 작업자 그리기는 브라우저별 지원(OffscreenCanvas)과 구조 변경이 부담.
- **비용**: 서버 없음.
- **보안**: 변화 없음.
- **오프라인과 대체**: 그대로.
- **작업량**: 작음(칸 수 자동 조절, 안 보이는 칸 건너뛰기, 시작값 측정과 조정) ~ 중간(작업자 그리기).
- **잃는 것**: 없음. 화질 상한만 있다.

## 6. 추천과 이유

1. **E를 먼저 한다**(작은 일). 측정 2에서 비용이 칸 수에 비례했으므로, 기기 성능에 맞춰 칸 수와 갱신 간격을 자동으로 낮추고, 화면 밖 칸을 건너뛰고, `CCTV_LIMITS` 시작값을 실제 기기에서 재서 확정한다. 서버도 비용도 안 들고 정적 배포를 지킨다.
2. **B와 D는 보류하고, 조건이 갖춰지면 D로 간다.** 조건: ① 서버 인증과 접속 수 제한이 끝남, ② GPU가 있는 서버를 켤 수 있음(본인 PC로 면접 시연이라도), ③ 카메라와 온도 색 처리 방식을 정함. D는 서버가 없을 때도 A로 돌아가므로 정적 사이트의 장점을 잃지 않는다. B만 하면 서버가 없을 때 CCTV가 사라지므로 D로 하는 것이 낫다.
3. **C는 하지 않는다.** 접속자마다 GPU가 들고, 터치가 안 되고, 정적 배포를 잃는다. Unreal 클라이언트의 Pixel Streaming은 ADR-004대로 시연용으로 따로 둔다.
4. 포트폴리오 이야기로는 "Omniverse가 서버에서 시뮬레이션과 장면을 그릴 수 있음(ovrtx 1280 x 720 약 15 ms/프레임, 이 PC 기준 시각화 측정)을 확인했고, 브라우저 비용을 먼저 줄인 뒤 서버 그리기는 선택 기능으로 설계했다"가 정직하고 확장 가능성도 보인다.

## 7. 사용자가 정해야 할 것

1. **서버 그리기를 공개로 열 것인가?** 열려면 GPU 서버(상시/임시/본인 PC)와 인증이 필요하다. 아니면 "본인 PC로 시연할 때만"으로 한정할 것인가?
2. **GitHub Pages 정적 사이트가 계속 기본인가?** 그렇다면 D(서버 없으면 A)만 허용된다.
3. **CCTV 칸에서 랙을 눌러 선택하는 기능이 필요한가?** 필요하면 B/D에서 라벨 영상 또는 서버 쪽 선택 처리가 필요하다.
4. **서버 그리기 화면과 브라우저 화면의 모양 차이를 받아들일 것인가?** (같은 장면이어도 그리기 방식이 달라 색과 그림자가 다를 수 있다.)
5. **E를 지금 진행해도 되는가?** (`CCTV_LIMITS` 시작값 조정, 자동 낮춤 규칙)
6. **GPU 컨테이너를 만들 것인가?** Docker Engine은 이미 설치했고 CPU 서버 이미지는 확인했다. 서버 그리기를 컨테이너로 돌리려면 NVIDIA 컨테이너 런타임 같은 GPU 설정이 더 필요하다(미확인).
7. **영상 방식**: 전송량이 중요하면 WebP/H.264, 단순함이 중요하면 JPEG. 지연 목표를 정할 것인가?

## 9. 측정 재현 방법

```powershell
# 서버 그리기 (이 폴더에서 실행): experiments/omniverse_probe
uv run --python 3.13 python bench_ovrtx_frames.py
```

- 처음 실행은 셰이더 준비로 오래 걸릴 수 있다. 결과는 `out/bench_ovrtx_frames.json`. 종료 시 멈추는 현상을 피하려고 결과 저장 후 바로 끝낸다(`probe_ovrtx_outputs.py`와 같은 방식).
- 브라우저 비교는 저장소에 스크립트를 넣지 않았다. 방법은 3.2에 적었다(`window.__viewer.scene._renderCctv` 호출 시간 측정).
- ovrtx 버전은 0.3.0.312915(E0 문서 확인값)이다. 지원 상태는 시기별로 변하므로 다시 쓰기 전에 공식 문서로 확인한다.
